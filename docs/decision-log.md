# StorageSlim 決定ログ

最終更新: 2026-08-23
ステータス: Draft

## 1. 目的

このファイルは、`StorageSlim` の未確定事項を1件ずつ記録し、判断内容と根拠を残すための決定ログです。

用途:

- 仕様の確定履歴を残す
- `docs/requirements.md` へ反映する前の判断を整理する
- GitHub Issue や PR で議論した内容の着地点を残す

## 2. 運用ルール

1. 1テーマにつき1エントリを作成する
2. 各エントリは `状態` を持つ
3. `決定` だけでなく `理由` と `影響` を残す
4. 決定後は `docs/requirements.md` に反映する
5. 実装上の制約で覆る可能性がある場合は、その条件を明記する

状態の定義:

- `未決定`
- `提案済み`
- `検証中`
- `決定済み`
- `保留`

## D-07 デスクトップフレームワーク選定

- 状態: 決定済み
- 分類: 技術選定
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

Windows / macOS 両対応で、モダンかつ安定したデスクトップアプリ基盤をどうするか。

### 選択肢

- Tauri
- Electron
- Flutter
- OS ごとの別実装

### 決定

- 初期版のデスクトップフレームワークは `Tauri` を採用する
- 実装開始条件として、開発環境に Rust toolchain を導入する
- Windows では Tauri 公式前提どおり `Microsoft C++ Build Tools` と `WebView2` を必須前提とする
- `Electron` は、Tauri と画像処理スタックの統合で重大な阻害要因が出た場合のみ再検討する

### 理由

- Tauri 公式ドキュメント上で Windows / macOS 向けの継続的な配布前提が明確であり、ローカル完結型デスクトップアプリの構成に適している
- ファイルシステム連携は Tauri のプラグインまたは Rust バックエンドで扱え、今回のローカル一括処理要件と整合する
- Web UI とネイティブ処理を分離しやすく、画像処理やタイムスタンプ補正を Rust 側に寄せた構成が取りやすい
- 現在のローカル環境では `rustc` / `cargo` は未導入だが、これは採用阻害ではなく実装前のセットアップ課題と判断できる

### 影響

- Rust 連携前提の設計が必要
- 開発開始前に Windows / macOS それぞれのビルド前提を整える必要がある
- ネイティブライブラリとの接続方法を Rust 側で確定する必要がある

### 保留条件 / 再確認条件

- Tauri と採用ライブラリの統合で、必須形式またはタイムスタンプ補正に致命的な制約が出た場合のみ再評価する

## D-08 画像処理ライブラリ選定

- 状態: 決定済み
- 分類: 技術選定
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

対応形式、速度、安定性、配布容易性の観点から画像処理ライブラリをどうするか。

### 選択肢

- Sharp / libvips 系
- ImageMagick 系
- 形式ごとにライブラリを分ける

### 決定

- 初期版の中核画像処理ライブラリは `libvips 系` を採用する
- Rust 統合は `libvips` の Rust バインディングを第一候補とする
- HEIC / HEIF の再出力互換性やアニメーション GIF の細部で不足が出た場合に限り、補助ライブラリの併用を許容する
- 初期版では `形式ごとに全部別` の分散構成は避ける

### 理由

- libvips 公式情報で JPEG / PNG / WebP / GIF / HEIC / AVIF を含む広い形式対応が確認できる
- メタデータ保持に関する `keep` 系オプションがあり、`メタデータ保持はベストエフォート` という要件と整合する
- マルチページ画像としての保存オプションがあり、アニメーション GIF を初期版対象に含める方針と整合しやすい
- 高速性とメモリ効率に優れ、バッチ処理中心の要件に合う

### 影響

- Rust 側では `libvips` ネイティブライブラリとバインディングの導入手順を整える必要がある
- Windows / macOS のビルド環境に `libvips` をどう配布同梱するかの設計が必要になる
- HEIC / HEIF の OS 差分とアニメーション GIF の最終対応表は実装時に実機確認が必要になる

### 保留条件 / 再確認条件

- 必須形式への対応不足、または Rust バインディング上の重大な制約が確認された場合のみ補助ライブラリ併用を前提に再設計する

## D-11 HEIC / HEIF の Windows / macOS 実装制約

- 状態: 決定済み
- 分類: 実装方針
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

HEIC / HEIF の読込と `オリジナル形式を維持` 再出力を、Windows / macOS の両方でどこまで初期版仕様として約束するか。

### 選択肢

- 両 OS で無条件に読込 / 再出力可能とみなす
- 読込は両 OS 対応とし、再出力は build 条件付き機能として扱う
- 初期版では HEIC / HEIF 再出力自体を対象外にする

### 決定

- HEIC / HEIF の読込は Windows / macOS の両方で初期版対象とする
- `オリジナル形式を維持` 再出力は、HEIF エンコーダを同梱したビルドに限って提供する
- エンコーダ未同梱ビルドでは、対象ファイル単位で理由付き失敗を返す
- したがって HEIC / HEIF 再出力は `無条件保証` とは表記しない

### 理由

- libvips は libheif 経由で HEIF 保存機能を持つ
- ただし libheif は HEIC encode に codec backend を必要とし、README では `x265` を使う場合 GPL であることが明記されている
- codec plugin 構成で配布物を分けられるため、再出力は build 条件付き機能として定義するのが最も現実的

### 影響

- 初期版の仕様書と UI に `HEIC / HEIF 再出力は build 条件付き` の注記が必要になる
- バッチ処理では対象ファイル単位の失敗理由表示が重要になる
- 配布設計で HEIF encoder backend の同梱方針を決める必要がある

### 保留条件 / 再確認条件

- 実装時に採用する HEIF encoder backend の配布方式が確定した時点で、最終文言を微調整する

## D-13 寸法上限の扱い（書ける寸法と読める寸法の差）

- 状態: 決定済み
- 分類: 仕様
- 優先度: 高
- 決定日: 2026-08-15
- 決定者: User

### 論点

エンコーダが受け付ける寸法と、主要なデコーダが読める寸法が形式ごとに一致しない。どちらを上限として採用するか。

### 選択肢

- 規格上の上限を採用し、開けないファイルの生成を許容する
- 読める側の上限を採用し、一律で失敗させる
- 形式ごとに、失敗と警告を使い分ける

### 決定

- WebP 16,383 px / GIF 65,535 px / JPEG 65,500 px / AVIF 65,535 px を超える場合は失敗させる
- JPEG は規格上の 65,535 ではなく libjpeg の 65,500 を採用する
- AVIF の 32,768 px 超は失敗ではなく警告付きの成功とする
- PNG は寸法上限を設けない
- 判定はリサイズ後の寸法に対して行う

### 理由

- JPEG は libjpeg 系がほぼ唯一の実装であり、65,501〜65,535 で書いたファイルは事実上どこでも開けない。失敗させる方が実害が小さい
- AVIF は libavif が既定 32,768 で切る一方、libheif 系では読める。ファイル自体は仕様上正常なため失敗扱いは過剰であり、警告に留める
- 上限超過はエンコーダ側でパニックしたり、無警告で壊れた出力になったりする。事前判定で理由の分かるエラーに変換する

### 影響

- WebP 出力時の `VP8_ENC_ERROR_BAD_DIMENSION` パニックが、理由の分かるエラーに置き換わる
- GIF 出力時の `as u16` によるサイレントな破損が防止される
- 32,769〜65,535 px の AVIF は生成できるが、警告が付く

### 保留条件 / 再確認条件

- libavif の既定上限が変わった場合は 32,768 の見直しが必要

## D-17 画像圧縮と動画圧縮の UI 分離方式

- 優先度: 高

- 決定者: User

## D-18 動画エンコーダの調達方針とライセンス

- 状態: 決定済み
- 分類: 技術
- 優先度: 高
- 決定日: 2026-08-22
- 決定者: User

### 論点

動画エンコード手段をどう調達するか。また、GitHub での MIT 無償公開と BOOTH でのビルド代行販売（300-500 円想定）に両立する構成はどれか。

### 選択肢

- GPL ビルドの FFmpeg を同梱し、`libx264` / `libx265` を使う
- LGPL ビルドの FFmpeg を同梱し、H.264 は OS / ハードウェアエンコーダを使う
- FFmpeg を同梱せず、システム導入済みのものを検出して使う
- `ffmpeg-next`（libav バインディング）でプロセス内エンコードする

### 決定

- **LGPL ビルドの FFmpeg を sidecar（`externalBin`）として同梱し、CLI で駆動する**
- あわせて `外部 ffmpeg のパスを指定する` 設定を用意し、ユーザーが持ち込んだフルビルドも使えるようにする
- H.264 は OS / ハードウェアエンコーダ（Windows: Media Foundation / NVENC / QSV / AMF、macOS: VideoToolbox）を使う
- AV1 / VP9 は BSD ライセンスの SVT-AV1 / libvpx を使う
- `libx264` / `libx265` を含む GPL ビルドは同梱しない
- FFmpeg バイナリは git 管理対象外とし、取得スクリプトで `src-tauri/binaries/` へ配置する
- `THIRD-PARTY-NOTICES.md` に LGPL 2.1 全文・FFmpeg のバージョン・configure オプション・同一リビジョンのソース入手先を記載する
- BOOTH の商品説明に `再配布禁止` 等の追加制限を記載しない。ソース公開と自前ビルド可能であることを明記し、ビルド済みバイナリの提供を対価とする

### 理由

- `libx264` / `libx265` は GPL であり、GPL ビルドを同梱すると本体を MIT のまま配布できるかがグレーになる
- 別プロセス（sidecar）呼び出しであるため、LGPL の「ライブラリ差し替え可能性」の要件を構造的に満たせる
- H.264 / HEVC には特許プールが存在するが、OS / ハードウェアエンコーダを使えばエンコーダ実装を自ら配布しないため、負担が OS / GPU ベンダー側に帰属する。有償配布を想定する以上この差は重要
- LGPL は LGPL 部分への追加制限を禁じているため、商品ページの定型文（再配布禁止）と衝突しないよう明記が必要
- CLI 駆動はクラッシュがアプリ本体に波及せず、`-progress pipe:1` で進捗が取れ、プロセス終了で確実に中断できる
- `ffmpeg-next` は Windows / macOS 両対応のビルド整備コストが高く、デコーダのパニックがアプリを落とす

### 影響

- インストーラサイズが 40-80 MB 増える
- `scripts/generate-notices.mjs` は cargo / npm しか走査しないため、FFmpeg 用の記載を別途持たせる必要がある
- macOS では `.app` 内の FFmpeg バイナリも個別署名が必要で、公証まで含めた確認が必要
- Windows は BtbN の `lgpl` 版が使えるが、macOS は LGPL 構成での自前ビルドが現実的
- `libx264` と同等の圧縮率は得られない。OS / ハードウェアエンコーダは CRF（固定品質）に非対応の経路があり、品質 UI の設計に影響する（`D-19` 参照）
- 法務の専門家確認は行っていない。販売規模が拡大した場合は再確認が必要

### 保留条件 / 再確認条件

- OS / ハードウェアエンコーダの H.264 出力品質が実用水準に達しない場合は、外部 ffmpeg 指定を前提とした案内強化、または配布ライセンスの見直しを再検討する
  - 2026-08-23 に計測。`h264_nvenc` の画質は x264 とほぼ同等だが指定ビットレートを 16% 超え、`h264_mf` は 25% 超過かつ画質も低い。**同一品質なら x264 より 15-25% 大きい**という結果で、実用範囲と判断し方針は変えない。圧縮率を求めるユーザー向けに `ffmpeg のパス` の存在を README へ明記した。計測値は `docs/format-matrix-video.md` の 9 章。
  - あわせて、`-encoders` に出るエンコーダが必ず動くとは限らないことが判明した（`h264_qsv` / `h264_amf` はこの環境で初期化に失敗）。存在確認だけで選ぶ実装は配布に耐えないため、1 フレーム試して動く経路を選ぶ方式へ変更した。
- 同梱する LGPL ビルドの入手経路が失われた場合は、自前ビルドへ切り替える

## D-19 動画の品質指定 UI

- 状態: 決定済み
- 分類: 仕様
- 優先度: 高
- 決定日: 2026-08-22
- 決定者: User

### 論点

画像側の `品質 1-100` に相当する指定を、動画でどう提示するか。

### 選択肢

- CRF を数値で直接指定させる
- プリセットのみを提示する
- プリセット主体とし、詳細モードで数値を開放する

### 決定

- 通常 UI は品質プリセット 4 段（`高画質` / `標準` / `小さめ` / `最小`）のみを提示する
- 内部で、選択中のコデックとエンコーダ経路に応じて CRF またはビットレートへマップする
- 詳細セクションで CRF の直接指定を開放するが、CRF 非対応のエンコーダ選択時は無効化して理由を表示する

- 動画は画像より結果サイズの予測が難しく、目安表示の効果が大きい

### 影響

- プリセットからエンコーダ経路別の指定値へマップするテーブルが必要
- ビットレート指定経路では、解像度 x fps から目標ビットレートを算出する処理が必要
- 詳細セクションに「無効化 + 理由表示」の状態が増える

### 保留条件 / 再確認条件

- 目安サイズの誤差が大きく誤解を招く場合は、表記を範囲（`約 ◯◯-◯◯ MB`）へ変更する

## D-20 動画処理の停止・一時停止仕様

- 状態: 決定済み
- 分類: 仕様
- 優先度: 高
- 決定日: 2026-08-22
- 決定者: User

### 論点

既存仕様の `停止時、現在処理中の 1 ファイルは完了させる` と `失敗時に 0 byte のファイルを残さない` を、動画にどう適用するか。

### 選択肢

- 現在のファイルを完走させる（既存仕様を踏襲）
- プロセスを強制終了し、書きかけのファイルを残す
- プロセスを強制終了し、書きかけのファイルを削除する
- stdin に `q` を送って正常終了させ、生成物を削除する

### 決定

- 停止時は FFmpeg の stdin に `q` を送り、コンテナを正しく閉じてから終了させる
- 生成された一時ファイル（`*.part`）は削除する
- 結果一覧には `中断（出力を破棄しました）` として記録する
- 停止ボタン付近の文言をモードで切り替える
  - 画像モード: `現在のファイルを完了してから停止します`
  - 動画モード: `現在のファイルの出力を破棄して停止します`
- 一時停止は Phase 1 ではファイル境界のみとし、ボタン表記を `次のファイルの前で一時停止` に変更する
- 動画の出力は一時ファイルへ書き出し、成功時にリネームする

### 理由

- 動画は 1 ファイルの処理が数分から数十分になるため、完走を待つ方式は「停止が機能していない」のと同じ体験になる
- 1080p 10 分の動画は生データで数十 GB になり、画像のようなメモリ完結が不可能。逐次書き出しが前提となる
- MP4 は末尾にヘッダ（moov atom）を書いて完成する形式のため、強制終了した生成物は多くの場合再生できない。「途中まで残す」は実質的に選択肢にならない
- `q` による正常終了なら、破損ファイルやファイルハンドルの残留を避けつつ数秒で停止できる
- 短く切れた正常な動画が残ると、圧縮ツールの成果物として誤解を招く
- Windows に `SIGSTOP` がないため、実行中プロセスの真の一時停止には `NtSuspendProcess` 相当の手段が必要で、Phase 1 に入れる価値が薄い

### 影響

- 既存要件の「エンコードはメモリ上で完了させてから書き出す」は画像固有の記述となり、動画は一時ファイル方式として別記が必要
- `ProcessResultItem` に `中断` を表す状態の表現が必要
- 停止・一時停止のボタン文言がモード依存になる
- エンコード中の真の一時停止は将来対応として残る

### 保留条件 / 再確認条件

- `q` 送信後に終了しないケースが確認された場合は、タイムアウト後の強制終了をフォールバックとして追加する

### requirements.md 反映要否

反映予定（`docs/requirements-video.md` と `docs/requirements.md` の該当節）

- 圧縮率の改善が体感できる幅がありながら、AV1 より再生環境の問題が起きにくい
- 1 形式を通せば、残りは同じ構造へ流し込むだけになる
- HEVC は `libx265` が GPL のため同梱できず、ハードウェアエンコーダ依存になる。先に入れると環境差で挙動が読めない

### 影響

- 出力形式が増えたため、対応マトリクスを `docs/format-matrix-video.md` へ分離した
- 音声モードの `AAC で再エンコード` を、コンテナ依存の `再エンコード` へ変更した（永続化値は `aac` から `reencode`。旧値は読み替える）
- `video_environment` は出力形式ごとの利用可否を返すようになった
- CRF の上限と既定値がコデック別になった。出力形式を切り替えると手動指定は破棄する
- WebM のエンコード速度は H.264 より大幅に遅い。UI で明示する

### 保留条件 / 再確認条件

- `libvpx-vp9` の速度が実用に耐えない場合は `-cpu-used` の既定値を見直す
  - 2026-08-23 に計測し、変更不要と判断した。4K 素材の 70 秒を 27 秒（約 2.6 倍速）で処理できている。計測値は `docs/format-matrix-video.md` の 8 章。

### requirements.md 反映要否

反映済み（`docs/requirements-video.md`、`docs/format-matrix-video.md`）

## D-22 macOS 向け FFmpeg の調達方法

- 状態: 決定済み
- 分類: 技術
- 優先度: 高
- 決定日: 2026-08-25
- 決定者: User

### 論点

`D-18` で LGPL ビルドの同梱を決めたが、macOS には LGPL 構成の配布ビルドが存在しない。BOOTH で macOS 版も売る前提に立つと、購入者が何も準備せずに動画圧縮を使える必要がある。

### 選択肢

- 同梱せず、購入者に `brew install ffmpeg` を案内する
- Homebrew のビルドをそのまま同梱する
- 公式ソースから LGPL 構成でビルドして同梱する

### 決定

- **公式ソース（`https://ffmpeg.org/releases/`）から LGPL 構成でビルドし、sidecar として同梱する**
- バージョンは固定し、tarball の sha256 を検証する
- H.264 と AAC は OS 内蔵の VideoToolbox / AudioToolbox を使い、追加ライブラリを持ち込まない
- WebM 出力に必要な libvpx と libopus（いずれも BSD）だけを静的リンクし、条文を `FFMPEG-STATIC-LIBS-LICENSE.txt` として同梱する
- 依存ライブラリも Homebrew のものは使わず、バージョンを固定してソースからビルドする
- 最低動作 OS は macOS 11 に固定し、ビルド後に `otool -l` の `minos` を検査する
- 自動検出で Homebrew の dylib を拾う機能（xcb / xlib / lzma）は明示的に無効化し、ビルド後に `otool -L` でシステム外の依存が無いことを検査する
- 配布対象は Apple Silicon（`aarch64-apple-darwin`）とする

### 理由

- 購入者に事前準備を求める形は、有償配布では問い合わせの主要因になる
- Homebrew のビルドは GPL 構成（`libx264` / `libx265` 入り）であり、`D-18` の方針では同梱できない
- Homebrew の dylib へ動的リンクした状態で配ると、購入者の環境では起動しない。静的リンクと依存検査でこれを構造的に防ぐ
- デプロイメントターゲットを指定しないと、ビルドしたマシンの OS バージョン（macOS 26）が最低要件として焼き込まれる。この状態で配ると「アプリは起動するが動画モードだけ動かない」という最も分かりにくい壊れ方をする。Homebrew の `libvpx.a` / `libopus.a` も同じ問題を持つため、依存ごとソースからビルドする
- Intel 版は x86_64 の依存ライブラリを別途用意する必要があり、費用と手間に対して需要が読めない

### 影響

- `scripts/fetch-ffmpeg.mjs` が OS ごとに分岐する（Windows は取得、macOS はビルド）
- macOS のビルドには Xcode Command Line Tools と `pkg-config` が必要。所要時間は 15 分程度
- macOS 版 dmg が 5.7 MB から 27 MB になった
- 商品ページに Apple Silicon 専用である旨の記載が必要

### 保留条件 / 再確認条件

- Intel Mac の購入希望が実際に出た場合、クロスビルドの構成を再検討する

### requirements.md 反映要否

不要（実装手段の話であり、要件は `D-18` のまま）
