# StorageSlim 決定ログ

最終更新: 2026-08-10
ステータス: Draft

## 1. 目的

このファイルは、`StorageSlim` の未確定事項を1件ずつ記録し、判断内容と根拠を残すための決定ログです。

用途:

- 仕様の確定履歴を残す
- `docs/requirements.md` へ反映する前の判断を整理する
- GitHub Issue や PR で議論した内容の着地点を残す

## 2. 運用ルール

1. 1テーマにつき1エントリを作成する
2. 各エントリは `状態` を持つ
3. `決定` だけでなく `理由` と `影響` を残す
4. 決定後は `docs/requirements.md` に反映する
5. 実装上の制約で覆る可能性がある場合は、その条件を明記する

状態の定義:

- `未決定`
- `提案済み`
- `検証中`
- `決定済み`
- `保留`

## D-01 メタデータ保持時の保持範囲

- 状態: 決定済み
- 分類: 仕様
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

`メタデータを保持する` を選んだ場合に、何を保持対象とみなすか。

### 選択肢

- EXIF / ICC profile / GPS 情報を含めて可能な限り保持する
- EXIF を優先して保持し、その他はベストエフォートとする
- 形式ごとに保持可能な範囲を定義する

### 決定

- EXIF / ICC profile / GPS 情報を含めて可能な限り保持する
- ただし形式やライブラリ制約で完全保持できない場合があることを許容する
- UI やドキュメントでは `保持はベストエフォート` であることを明示する

### 理由

- 保持を選ぶユーザーは位置情報を含む元情報の保存を期待しやすい
- 一方で完全保持を絶対要件にすると、対応形式やライブラリ選定が過度に縛られる

### 影響

- UI 文言に補足が必要
- ライブラリ選定時にメタデータ保持能力の確認が必要

### 保留条件 / 再確認条件

- 採用ライブラリ決定後に、形式ごとの実保持範囲を確認する

- 決定日: 2026-08-10
- 決定者: User

### 論点

`作成日時` と `更新日時` を個別に選択できる UI にするか、まとめて1項目にするか。

### 選択肢

- `作成日時を引き継ぐ` と `更新日時を引き継ぐ` を個別指定できる

- UI は個別指定にする
- 日本語ラベルは `作成日時を引き継ぐ` と `更新日時を引き継ぐ` を採用する

- 既存要件として `CreationTime` と `LastWriteTime` の両方を重視している
- 個別指定にすると利用者の要望に対応しやすい

### 影響

- 設定項目が1つ増える
- macOS 側で属性差分がある場合は補足が必要

### 保留条件 / 再確認条件

- `元ファイル名_出力形式名`

### 影響

- 既定出力先での運用説明が必要になる場合がある

再帰処理時に、出力先で同名フォルダが存在する場合や隠しファイルがある場合の扱いをどうするか。

### 選択肢

- フォルダ構造をそのまま再現し、同名時はマージする
- セッション単位の出力ルートを新規作成する

- システムファイルや隠しファイルを対象にすると意図しない処理が起きやすい

### 影響

- 出力先構造が長期運用で混在しやすくなる
- 命名規則への依存度が上がる

## D-05 アニメーション GIF から非アニメ形式へ変換する場合の扱い

- 状態: 決定済み
- 分類: 互換性
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

アニメーション GIF を JPEG / PNG / WebP / AVIF などへ変換する場合に、どう扱うか。

### 選択肢

- 先頭フレームのみを書き出す
- 非アニメ形式への変換は不可としてエラーにする
- アニメーション保持可能な形式への変換だけ許可する

### 決定

- アニメーション GIF から非アニメ形式への変換は初期版では不可とする
- ユーザーには理由が分かるエラーを表示する
- 将来的に `先頭フレームを書き出す` オプションを追加する余地は残す

### 理由

- 黙って先頭フレームだけ出すと、結果がユーザー期待から外れやすい
- 初期版では誤解の少ない挙動を優先した方が安全

### 影響

- 一部の変換組み合わせが制限される
- エラー理由の文言設計が必要になる

### 保留条件 / 再確認条件

- 将来的なアニメーション WebP / AVIF 対応状況に応じて再評価可能

- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

全入力形式から全出力形式への変換を目指すか、一部非対応組み合わせを許容するか。

### 選択肢

- 可能な限り全組み合わせ対応
- 実装難度や互換性上、非対応組み合わせを明示して許容する

### 決定

- 基本方針は `可能な限り多くの組み合わせに対応`
- ただし形式特性上の不整合が大きい組み合わせは非対応を許容する

## D-07 デスクトップフレームワーク選定

- 状態: 決定済み
- 分類: 技術選定
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

Windows / macOS 両対応で、モダンかつ安定したデスクトップアプリ基盤をどうするか。

### 選択肢

- Tauri
- Electron
- Flutter
- OS ごとの別実装

### 決定

- 初期版のデスクトップフレームワークは `Tauri` を採用する
- 実装開始条件として、開発環境に Rust toolchain を導入する
- Windows では Tauri 公式前提どおり `Microsoft C++ Build Tools` と `WebView2` を必須前提とする
- `Electron` は、Tauri と画像処理スタックの統合で重大な阻害要因が出た場合のみ再検討する

### 理由

- Tauri 公式ドキュメント上で Windows / macOS 向けの継続的な配布前提が明確であり、ローカル完結型デスクトップアプリの構成に適している
- ファイルシステム連携は Tauri のプラグインまたは Rust バックエンドで扱え、今回のローカル一括処理要件と整合する
- Web UI とネイティブ処理を分離しやすく、画像処理やタイムスタンプ補正を Rust 側に寄せた構成が取りやすい
- 現在のローカル環境では `rustc` / `cargo` は未導入だが、これは採用阻害ではなく実装前のセットアップ課題と判断できる

### 影響

- Rust 連携前提の設計が必要
- 開発開始前に Windows / macOS それぞれのビルド前提を整える必要がある
- ネイティブライブラリとの接続方法を Rust 側で確定する必要がある

### 保留条件 / 再確認条件

- Tauri と採用ライブラリの統合で、必須形式またはタイムスタンプ補正に致命的な制約が出た場合のみ再評価する

## D-08 画像処理ライブラリ選定

- 状態: 決定済み
- 分類: 技術選定
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

対応形式、速度、安定性、配布容易性の観点から画像処理ライブラリをどうするか。

### 選択肢

- Sharp / libvips 系
- ImageMagick 系
- 形式ごとにライブラリを分ける

### 決定

- 初期版の中核画像処理ライブラリは `libvips 系` を採用する
- Rust 統合は `libvips` の Rust バインディングを第一候補とする
- HEIC / HEIF の再出力互換性やアニメーション GIF の細部で不足が出た場合に限り、補助ライブラリの併用を許容する
- 初期版では `形式ごとに全部別` の分散構成は避ける

### 理由

- libvips 公式情報で JPEG / PNG / WebP / GIF / HEIC / AVIF を含む広い形式対応が確認できる
- メタデータ保持に関する `keep` 系オプションがあり、`メタデータ保持はベストエフォート` という要件と整合する
- マルチページ画像としての保存オプションがあり、アニメーション GIF を初期版対象に含める方針と整合しやすい
- 高速性とメモリ効率に優れ、バッチ処理中心の要件に合う

### 影響

- Rust 側では `libvips` ネイティブライブラリとバインディングの導入手順を整える必要がある
- Windows / macOS のビルド環境に `libvips` をどう配布同梱するかの設計が必要になる
- HEIC / HEIF の OS 差分とアニメーション GIF の最終対応表は実装時に実機確認が必要になる

### 保留条件 / 再確認条件

- 必須形式への対応不足、または Rust バインディング上の重大な制約が確認された場合のみ補助ライブラリ併用を前提に再設計する

## D-09 HEIC / HEIF の実装実現性

- 状態: 決定済み
- 分類: 実装方針
- 優先度: 高
- 決定日: 2026-08-10
- 決定者: User

### 論点

初期版で `HEIC / HEIF` の入力と、`オリジナル形式を維持` した再出力を Windows / macOS の両方で実用レベルに提供できるか。

### 選択肢

- 両 OS で同等対応を目指す
- OS ごとの差分を許容して制約付きで提供する
- 初期版では制限を明記する

### 決定

- 目標は `両 OS で入力対応 + オリジナル形式維持再出力`
- ただし実装検証で差分が出た場合は、OS ごとの差分を明記して制約付き提供を許容する
- 初期版から完全同等対応を絶対条件にはしない

### 理由

- 要件上は重要だが、OS とライブラリ依存が強い可能性が高い
- 理想条件で固定しすぎると全体開発が止まりやすい

### 影響

- 初期版の対応表記に注意が必要
- ライブラリ選定とフレームワーク選定に強く影響する

### 保留条件 / 再確認条件

- 実ライブラリで Windows / macOS の両方を検証した後に最終運用制約を確定する
