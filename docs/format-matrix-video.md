# StorageSlim 動画出力形式対応マトリクス

最終更新: 2026-08-23
ステータス: Phase 1 + WebM 実装済み

## 1. 目的

動画圧縮モードの出力形式ごとの対応状況を定義します。画像側は `docs/format-matrix.md` を参照します。

出力形式の選択肢は、実際に使う FFmpeg のビルドに含まれるエンコーダによって変わります。アプリは起動時に `ffmpeg -encoders` を確認し、使えない形式を選択できないようにします。

## 2. 出力形式

| 出力形式 | コンテナ | 映像 | 音声 | 状態 |
| --- | --- | --- | --- | --- |
| MP4 (H.264) | MP4 | H.264 | AAC | 実装済み |
| WebM (VP9) | WebM | VP9 | Opus | 実装済み |
| MP4 (HEVC) | MP4 | HEVC | AAC | 未実装 |
| MP4 (AV1) | MP4 | AV1 | Opus | 未実装 |
| オリジナル維持 | 入力と同一 | 入力と同一 | - | 未実装 |

## 3. 入力から出力

入力コンテナは `mp4` / `mov` / `m4v` / `webm` / `mkv` / `avi` / `wmv` / `mts` / `m2ts` を受け付けます。判定は拡張子ではなく `ffprobe` の映像ストリーム有無で行うため、入力コデックは制限しません。

| 入力 | MP4 (H.264) | WebM (VP9) |
| --- | --- | --- |
| すべての対応入力 | 可 | 可 |

いずれの出力形式でも再エンコードします。入力コンテナは維持されません。

## 4. 映像エンコーダの選択順

上から順に、FFmpeg に含まれているものを使います。

| 出力形式 | 優先順 | レート制御 |
| --- | --- | --- |
| MP4 (H.264) | `libx264` | CRF |
| | `h264_nvenc` / `h264_qsv` / `h264_amf` / `h264_videotoolbox` / `h264_mf` / `libopenh264` | ビットレート |
| WebM (VP9) | `libvpx-vp9` | CRF |
| | `vp9_qsv` | ビットレート |

`D-18` により同梱ビルドは LGPL 構成で `libx264` を含みません。そのため H.264 は通常 OS / ハードウェアエンコーダが選ばれ、CRF は使えません。VP9 の `libvpx` は BSD ライセンスのため、同梱ビルドでも CRF が使えます。

## 5. 品質プリセットの対応値

CRF の実用レンジはコデックごとに異なります。同じ数値でも意味が変わるため、UI では数値ではなくプリセットを主体にしています（`D-19`）。

| 出力形式 | 高画質 | 標準 | 小さめ | 最小 | CRF 上限 |
| --- | --- | --- | --- | --- | --- |
| MP4 (H.264) | 18 | 23 | 28 | 32 | 51 |
| WebM (VP9) | 28 | 33 | 38 | 43 | 63 |

ビットレート指定経路では、解像度 x fps x bits per pixel から算出します。VP9 は同じ体感画質をより少ないビットで出せるため、係数を 0.65 倍しています。

## 6. 音声

| 出力形式 | そのままコピーできる入力 | 再エンコード先 |
| --- | --- | --- |
| MP4 (H.264) | AAC / MP3 / ALAC | AAC |
| WebM (VP9) | Opus / Vorbis | Opus（`libopus`、無い場合は内蔵 `opus` + `-strict -2`） |

`そのままコピー` を選んでいても、コンテナに入れられない音声は再エンコードし、警告を表示します。MP4 は Opus を、WebM は AAC を格納できません。

## 7. 形式固有の注意

### WebM (VP9)

- エンコードが H.264 より大幅に遅い。`libvpx-vp9` は `-cpu-used 2` で実用速度に寄せている。
- `-b:v 0` を併記しないと CRF が効かない。
- 再生できないアプリがある。ブラウザは概ね対応。
- `-movflags +faststart` は MP4 muxer 固有のため付けない。

### MP4 (H.264)

- 同梱の LGPL ビルドでは OS / ハードウェアエンコーダになるため、出力品質が実行環境に依存する。
- `+faststart` を付けてストリーミング再生に適した配置にする。

## 8. 計測記録

出力形式を選ぶ判断材料として実測した値です。素材依存が大きいため、傾向の把握にのみ使います。

計測日: 2026-08-23  
条件: 長辺 640 px / 30 fps 上限 / 品質 `標準` / 音声 128 kbps 再エンコード / メタデータ削除  
環境: Windows / FFmpeg n4.4.3（GPL ビルド、`libx264` と `libvpx-vp9` はどちらもソフトウェア CRF 経路）

| 素材 | 元 | MP4 (libx264) | WebM (libvpx-vp9) | サイズ差 | 時間差 |
| --- | --- | --- | --- | --- | --- |
| 4K 横 1:10 (h264 / pcm_s16be) | 896 MB | 3.6 MB / 13.8 秒 | 2.5 MB / 27.3 秒 | -31% | +98% |
| 4K 縦 0:27 (hevc / aac) | 137 MB | 2.6 MB / 18.8 秒 | 2.4 MB / 23.6 秒 | -8% | +26% |
| 合計 | 1.0 GB | 6.2 MB / 32.5 秒 | 4.9 MB / 50.9 秒 | -21% | +57% |

音声分を差し引くと、映像だけでは -44% と -9%。**VP9 の効果は素材で大きく変わり、常に小さくなるとは言えません。**

判断:

- VP9 の速度は 70 秒の素材を 27 秒（約 2.6 倍速）で処理できており、実用範囲。`-cpu-used` の既定値 `2` は変更しない。
- 圧縮率を優先する用途では VP9 に価値があるが、既定は互換性を取って MP4 のままとする。

限界:

- 素材 2 本のみ。1 台の環境のみ。
- OS / ハードウェアエンコーダ経路（同梱 LGPL ビルドで実際に選ばれる経路）は未計測。これは `ISS-16` の対象。

## 9. 計測記録: OS / ハードウェアエンコーダ経路

同梱する LGPL ビルドで実際に選ばれる経路の計測です（`ISS-16`）。

計測日: 2026-08-23
FFmpeg: `N-126242-geb0bfa852e-20260822`（BtbN の win64-lgpl。`--disable-libx264 --disable-libx265`）
素材: 1080p30 / 10 秒の合成映像（`testsrc2`）
条件: 全エンコーダ共通で `-b:v 3000k -maxrate 4500k -bufsize 9000k`（目標 3.75 MB）
品質評価: `libvmaf`（同一ソースに対するスコア。値が大きいほど高品質）

### 9.1 この環境で動くか

| エンコーダ | 起動 | 備考 |
| --- | --- | --- |
| `h264_nvenc` | ○ | NVIDIA GPU あり |
| `h264_qsv` | × | `Error creating a MFX session: -9` |
| `h264_amf` | × | `DLL amfrt64.dll failed to open` |
| `h264_mf` | ○ | Media Foundation。ハードウェアが無くても動く |
| `libopenh264` | ○ | ソフトウェア。最終手段 |

**`-encoders` の一覧に出ることと、その環境で動くことは別問題です。** LGPL ビルドには nvenc / qsv / amf がすべて含まれるため、一覧だけで選ぶと対応 GPU の無い環境で毎回失敗します。アプリは 1 フレームだけ試して動く経路を選びます。

### 9.2 サイズと品質

| エンコーダ | 出力 | 目標との差 | VMAF |
| --- | --- | --- | --- |
| `libx264`（GPL。同梱しない。参考値） | 3.74 MB | -0% | 71.2 |
| `h264_nvenc` | 4.33 MB | **+16%** | 70.8 |
| `h264_mf` | 4.66 MB | **+25%** | 68.3 |
| `libopenh264` | 3.70 MB | -1% | 67.3 |

読み取れること:

- `h264_nvenc` の画質は x264 とほぼ同等（-0.4）だが、**指定ビットレートを 16% 超える**。同一品質あたりのサイズでは x264 が有利。
- `h264_mf` は超過が 25% と大きく、画質も 3 ポイント低い。ハードウェアが無い環境の受け皿がこれになるため、最も条件が悪い組み合わせ。
- `libopenh264` は目標を守るが画質は 4 ポイント低い。
- 総じて、**同梱の LGPL 経路は同一品質なら x264 より 15-25% 大きくなる**。実用範囲ではあるが、圧縮率を重視するユーザーには `ffmpeg のパス` で GPL ビルドを指定する価値がある。

限界:

- 合成映像 1 本・1 ビットレート・1 台の環境のみ。実写での傾向は異なる可能性がある。
- VMAF は合成映像に対しては実写ほど信頼できない。相対比較にのみ使っている。
- `h264_qsv` / `h264_amf` / `h264_videotoolbox` は未計測（この環境で動かない、または別 OS）。

未対応として残すこと:

- ビットレート超過を抑えるために `-maxrate` の係数（現在 1.5 倍）を下げる案がある。ただし合成映像 1 本の結果で調整すると複雑な実写で画質を落としかねないため、実写での再計測まで保留する。
